The `rabi` node consumes the shared `rabi_amplitude` QProgram from `qili-qprograms` (QHC-1914) instead of a local copy.

- The QProgram is built by `qili_qprograms.experiments.rabi_amplitude`, which plays the calibrated `pi-<operating_point>` pulse (normalised to unit amplitude) through a gain sweep and reads the `readout-<operating_point>` pulse, its weights and the drive/readout IFs from the calibration file. The node builds it and runs it directly -- no `experiment_class` driver layer -- setting the operating point's LOs, readout attenuation and drive source through the base node's shared `_set_operating_point_hardware` (`drive_power` for a Rohde & Schwarz source, `drive_gain` for a QCM-RF), then streaming the sweep. Optional step parameters default through the node's `defaults`; `ringup_time` is now `readout_ringup_time` and `drive_sigmas` is `drive_n_sigmas`, and the example tree's `rabi` defaults use `drive_amplitude_sweep`.
- The drive shape is now the stored `pi-<op>` DRAG pulse rather than one rebuilt from `drive_duration`/`drive_sigmas`/`drive_drag` step parameters, and the gain average runs inside the hardware sweep (qili's convention). The local `qprogram/rabi.py` and `experiment_classes/rabi.py` are removed; the reusable measurement-id helper moves to `experiments/results.py`.
- The pulses `rabi` reads and writes are the ones `rabi_amplitude` plays, named with qili-qprograms' `pulse_name` (ADR-0008): the fitted pi amplitude goes into `pi-<operating_point>` and the readout levels are tagged `readout-<operating_point>`, no longer the default `drag` and `readout` names the QProgram never played. Both pulses must already exist (they come with the manual calibration): a missing one, or a section naming a different pulse for the role, fails the step before any hardware is set. The node seeds no DRAG pulse, so the `drive_pulse`, `readout_pulse`, `drive_duration`, `drive_n_sigmas` and `drive_drag` step keys are gone.
