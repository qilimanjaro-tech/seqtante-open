Rewrote the calibration-tree parser for the tree of named steps (ADR-0003), with parameters resolved per target (ADR-0005). `CalibrationParser(calibration_config, platform).parse()` returns a `list[Pipeline]`, each with its `Step`s, and touches neither hardware nor the database.

- A tree has top-level `targets` and `defaults`, and `pipelines` of uniquely named `steps`. A step names its `experiment` and its `analysis` (the experiment's default when left out). Every other key, `operating_point` and `loop` included, is a parameter resolved per target, and is left for the node to validate. A pipeline can set `after` (a step or a list of steps of other pipelines), `enabled` and its own `targets`.
- Parameters resolve per target: `defaults.<experiment>`, then the step's own values, then every `overrides` entry whose `targets` include the target, in file order. An override naming a target the step doesn't run on logs a warning and is ignored for that target.
- Targets are `QubitTarget` and `CouplerTarget` objects. Every name in the tree is validated, `all_q` and `all_c` expand in place from the runcard's analog settings (an empty list is an error), and repeats are dropped, keeping the first.
- A malformed tree raises a `TreeParseError` whose message starts with the path, such as `pipelines.lz.steps.rabi_reset.analysis`. It is raised before the run is recorded in the database or the platform connects.

## **Example**
```yml
targets: [q1, q14]
defaults:
  two_tone: {freq_sweep: [-5e6, 5e6, 101], averages: 10000}
pipelines:
  sweet_spot:
    steps:
      sweet_spot_flux: {experiment: two_tone_vs_flux, analysis: parabola_vertex, operating_point: sweet_spot, loop: z}
      two_tone_sweet_spot: {experiment: two_tone, operating_point: sweet_spot}
  lz:
    after: sweet_spot_flux
    targets: [q14]
    steps:
      rabi_reset:
        experiment: rabi
        analysis: readout_levels
        operating_point: reset
        overrides:
          - targets: [q14]
            amplitude_sweep: [0.02, 0.5, 25]
```
